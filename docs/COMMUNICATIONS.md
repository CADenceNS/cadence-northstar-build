# Clinical Communications Platform

## Purpose

Clinical Communications is NorthStar's permanent operational-history layer. It is not a real-time chat product. It records clinically and operationally relevant communication in durable chronological order and binds that history to the entities that laboratory teams already use.

## Domain boundaries

Operational communication is stored separately from security audit history:

- **Communication events** contain business and clinical content that authorized users need to read during case execution.
- **System events** are communication events generated by NorthStar when an operational transition should appear in an entity timeline.
- **Security audit events** prove who invoked authenticated mutations, whether authorization succeeded, and which protected endpoint was affected.

A communication mutation creates one append-only operational event. The existing security middleware records the authenticated request independently. The platform does not copy full communication content into the security audit table.

## Supported entities

Timelines and threads may be attached to:

- Practice
- Doctor
- Patient
- Case
- Shipment
- Invoice

The schema is entity-neutral so future production work items and other approved modules can join the same platform without creating parallel communication stores.

## Event model

Each event records:

- tenant
- related entity type and identifier
- optional thread
- event type
- immutable content
- authenticated actor identifier and display name
- actor role
- occurrence timestamp
- optional `version_of` reference
- zero or more existing ObjectStorage records

`communication_events` rejects `UPDATE` and `DELETE` at the database layer. Corrections are appended as new events and may point to the previous event through `version_of`.

## Threads

Threads group related events while preserving the master chronological timeline. Threads have subjects and lifecycle status, but thread event content remains append-only. A thread does not create a separate message store.

## Attachments

Communication attachments reference `object_records`. New uploads are written through the existing `ObjectStorage` abstraction, and existing object identifiers may be associated without duplicating bytes. Tenant ownership and soft-deletion state are checked before association.

Supported stored objects include clinical images, PDFs, STL, OBJ, PLY, DICOM, invoice PDFs, and shipping documents. Provider migration remains transparent to the communications domain because only object metadata and identifiers are stored in communication tables.

## Notifications

Notifications are durable recipient projections of communication events. Each notification records:

- recipient user
- priority
- category
- read timestamp
- source communication event

Sprint 11 provides in-application delivery only. Email, SMS, push, and external notification providers are deferred.

## Search

Search is tenant-scoped and supports:

- entity type and identifier
- actor
- event type
- date range
- PostgreSQL full-text keyword search

Results are ordered newest first and capped to a bounded result set. Entity timelines remain ordered oldest first so they read as a chronological history.

## Authorization

All communications routes execute behind Sprint 10 authentication, session, CSRF, and tenant middleware. Retrieval is available to authenticated roles that can access the application. Creation is denied to the read-only auditor role. Existing tenant and administrative context remains authoritative.

More granular practice- and entity-specific grants can be added when Doctor Portal and external Practice users are introduced. Those future controls must extend, not bypass, Sprint 10 authorization.

## APIs

- `GET /api/communications/timeline`
- `POST /api/communications/events`
- `GET /api/communications/threads`
- `POST /api/communications/threads`
- `GET /api/communications/threads/:id`
- `GET /api/communications/search`
- `GET /api/notifications`
- `POST /api/notifications/:id/read`

Every mutation requires the active server session and valid CSRF state.

## React integration

The reusable `CommunicationTimeline` component is embedded in Practice, Doctor, Patient, Case, Shipment, and Invoice views. It retrieves chronology only when expanded and submits events through the protected API. `Notifications` provides authenticated in-application unread and read state.

## Deferred

- External email, SMS, or push delivery
- Mention parsing and user directory autocomplete
- Configurable notification rules
- Doctor Portal and Patient Portal external communication policies
- Retention automation and legal hold workflows
- Rich-text editing
- Real-time websocket presence or typing indicators
- Automated import of third-party email conversations
