# Clinical Communications Platform

## Purpose

Clinical Communications is NorthStar's permanent operational-history layer. It is not a real-time chat product. It records clinically and operationally relevant communication in durable chronological order and binds that history to the entities that laboratory teams already use.

The architectural decision is recorded in `docs/ADR/ADR-005-communications-operational-history.md`.

## Domain boundaries

Operational communication is stored separately from security audit history:

- **Communication events** contain business and clinical content that authorized users need during case execution.
- **System events** are operational timeline entries generated by NorthStar.
- **Security audit events** record authenticated communication mutations using minimized metadata only.

A communication mutation creates one append-only operational event. Thread creation, event creation, attachment and notification association, and notification read transitions also create immutable security audit evidence containing actor, entity, operation, identifiers, and counts. Full communication content is not copied into `audit_events`.

## Supported entities

Timelines and threads may be attached to Practice, Doctor, patient, case, shipment, and invoice records.

## Entity-bound authorization

Every communication route uses the reusable `EntityAccessService`. The service resolves the entity's durable ownership and evaluates:

- authenticated tenant membership;
- Practice authorization;
- Doctor ownership for Doctor-role identities;
- location restrictions when an entity carries location scope;
- read versus write mode;
- explicit administrative override.

The same service protects timeline retrieval, thread retrieval and creation, event creation, search results, attachment association, notification retrieval, and notification recipient association. Search results are filtered by authorized entity scope rather than tenant alone.

## Event model

Each event records tenant, entity type and ID, optional thread, event type, immutable content, authenticated actor and role, occurrence time, optional `version_of`, and zero or more ObjectStorage references.

`communication_events` rejects `UPDATE` and `DELETE` at the database layer. Corrections are appended as new events and may reference the previous event through `version_of`.

## Threads

Threads group related events while preserving the master chronology. Application validation and a composite PostgreSQL foreign key require every threaded event to match the thread's tenant, entity type, and entity ID.

## Attachments

New uploads use the existing `ObjectStorage` abstraction. Existing object associations are authorized against the object's owning entity before linking.

Public communication responses expose only safe metadata:

- object ID;
- file name;
- MIME type;
- byte size;
- object kind.

Provider names, buckets, object keys, credentials, and other storage implementation details are not public API fields. Authorized download endpoints or short-lived provider URLs remain the future download boundary.

## Notifications

Notification recipients must be active users with an identity membership in the authenticated tenant and must be authorized to read the associated entity. Each notification records recipient, priority, category, source event, creation time, and read time.

Sprint 11 provides in-application delivery only. Email, SMS, push, and external providers remain deferred.

## Search

Search supports entity, actor, event type, date range, and PostgreSQL full-text keywords. The database query is tenant-scoped and the returned records are additionally filtered through `EntityAccessService`.

## APIs

- `GET /api/communications/timeline`
- `POST /api/communications/events`
- `GET /api/communications/threads`
- `POST /api/communications/threads`
- `GET /api/communications/threads/:id`
- `GET /api/communications/search`
- `GET /api/notifications`
- `POST /api/notifications/:id/read`

Every mutation requires the active HttpOnly server session and valid CSRF state.

## React integration

The reusable `CommunicationTimeline` component is embedded in Practice, Doctor, patient, case, shipment, and invoice views. `Notifications` provides authenticated in-application unread and read state.

## Validation requirements

Communications validation includes:

- same-tenant, different-Practice denial;
- cross-tenant and cross-entity thread rejection;
- unauthorized event creation;
- search filtering by authorized Practice;
- unauthorized existing-object association;
- invalid and unauthorized recipient rejection;
- safe attachment response metadata;
- append-only database enforcement;
- minimized immutable security audit evidence;
- migration rollback and reapplication;
- Runtime Validation and full Playwright regression.

## Deferred

- External email, SMS, or push delivery
- Mention parsing and user-directory autocomplete
- Configurable notification rules
- Doctor Portal and Patient Portal external communication policies
- Retention automation and legal-hold workflows
- Rich-text editing
- Real-time websocket presence or typing indicators
- Automated import of third-party email conversations
- Authorized attachment download and short-lived provider URL endpoint
